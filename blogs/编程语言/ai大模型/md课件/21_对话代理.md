# 21 对话代理

## 学习目标
1. 掌握基于 LangGraph 构建对话代理的方法
2. 理解消息列表（`messages`）在对话状态中的作用
3. 能够实现具备历史记忆和上下文理解的对话机器人
4. 理解 `HumanMessage`、`AIMessage`、`SystemMessage` 的区别
5. 学会用检查点机制保存多轮对话状态

## 1. 什么是对话代理

对话代理可以理解为一个能够和用户连续交流的 AI 程序。

普通的大模型调用通常是这样的：

```
用户输入 -> 模型回答 -> 结束
```

而对话代理更像这样：

```
用户第 1 轮输入 -> 模型回答
用户第 2 轮输入 -> 模型结合上一轮继续回答
用户第 3 轮输入 -> 模型继续理解上下文
```

它和一次性问答最大的区别是：**对话代理需要记住前面说过什么。**

例如用户先说：

```text
我叫小王。
```

下一轮再问：

```text
我叫什么？
```

如果代理能回答‘你叫小王’，说明它具备了基本的对话记忆。

## 2. 为什么对话代理要用 `messages`

在 LangChain 和 LangGraph 中，对话通常不是用一个普通字符串保存，而是用消息列表 `messages` 保存。

一个简单的消息列表可能长这样：

```python
[
    HumanMessage(content='我叫小王'),
    AIMessage(content='你好，小王！'),
    HumanMessage(content='我叫什么？')
]
```

这个列表的好处是：

- 能保存多轮对话历史
- 能区分每句话是谁说的
- 能直接传给聊天模型
- 很适合放进 LangGraph 的状态里

可以把 `messages` 理解成一份‘聊天记录本’。每轮对话都会往记录本里追加新内容。

## 3. 三种常见消息类型

对话代理中最常见的消息类型有三种：

| 消息类型 | 含义 | 常见用途 |
| --- | --- | --- |
| `SystemMessage` | 系统消息 | 规定 AI 的角色、规则、风格 |
| `HumanMessage` | 用户消息 | 保存用户输入 |
| `AIMessage` | AI 消息 | 保存模型回复 |

举个例子：

- `SystemMessage`：你是一个耐心的 Python 老师
- `HumanMessage`：请解释什么是列表
- `AIMessage`：列表是 Python 中用于存放多个元素的数据结构

这三类消息合在一起，就能表达一段完整对话。

## 4. 第一个例子：手动维护消息列表

在进入 LangGraph 之前，先用一个最简单的例子理解 `messages`。

这个例子不调用大模型，只演示消息列表如何保存对话历史。

```python
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

messages = [
    SystemMessage(content='你是一个耐心的课程助教。'),
    HumanMessage(content='我叫小王。'),
    AIMessage(content='你好，小王，很高兴认识你。'),
    HumanMessage(content='我叫什么？')
]

for message in messages:
    print(type(message).__name__, ':', message.content)
```

### 代码解释

这个例子没有使用 LangGraph，也没有调用大模型，目的只是先把消息列表讲清楚。

#### `SystemMessage`
第一条消息是系统消息：

```python
SystemMessage(content='你是一个耐心的课程助教。')
```

它不是用户说的话，也不是模型回答的话，而是给模型设置角色和行为规则。

#### `HumanMessage`
用户说的话用 `HumanMessage` 表示。

例如：

```python
HumanMessage(content='我叫小王。')
```

这表示用户告诉代理：自己的名字是小王。

#### `AIMessage`
AI 的回复用 `AIMessage` 表示。

例如：

```python
AIMessage(content='你好，小王，很高兴认识你。')
```

它记录了上一轮模型回答过什么。

#### 为什么要保存完整列表
最后一条用户消息是：

```python
HumanMessage(content='我叫什么？')
```

如果只看这一句话，模型不知道‘我’是谁。

但如果把完整 `messages` 传给模型，模型就能从前面的聊天记录里看到：用户之前说过自己叫小王。

这就是对话历史的作用。

## 5. 在 LangGraph 状态中保存 messages

对话代理的核心状态通常就是 `messages`。

但是这里有一个重要细节：多轮对话不是每次覆盖旧消息，而是要把新消息追加到旧消息后面。

LangGraph 提供了 `add_messages`，可以帮助我们把消息列表自动追加合并。

下面先看一个不调用模型的 LangGraph 示例。

```python
from typing import Annotated
from typing_extensions import TypedDict
from langchain_core.messages import HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list, add_messages]

def simple_reply(state: ChatState):
    last_message = state['messages'][-1]
    reply = AIMessage(content=f'我收到了你的消息：{last_message.content}')
    return {'messages': [reply]}

builder = StateGraph(ChatState)
builder.add_node('simple_reply', simple_reply)
builder.add_edge(START, 'simple_reply')
builder.add_edge('simple_reply', END)

graph = builder.compile()
result = graph.invoke({
    'messages': [HumanMessage(content='你好，请介绍一下你自己')]
})

for message in result['messages']:
    print(type(message).__name__, ':', message.content)
```

### 代码解释

这个例子已经进入 LangGraph，但为了降低理解难度，暂时没有调用真正的大模型。

#### `Annotated[list, add_messages]`
这是本节最关键的一行：

```python
messages: Annotated[list, add_messages]
```

它表示：`messages` 是一个列表，并且当节点返回新的 `messages` 时，不是直接覆盖旧列表，而是把新消息追加进去。

如果没有 `add_messages`，你返回：

```python
{'messages': [reply]}
```

可能会覆盖原来的消息。

有了 `add_messages`，它的效果更像：

```python
旧消息列表 + 新消息列表
```

这正是多轮对话需要的行为。

#### `simple_reply` 节点
这个节点做了三件事：

1. 从 `state['messages']` 中取出最后一条消息
2. 根据最后一条用户消息生成一个简单回复
3. 把回复包装成 `AIMessage` 返回

这里的回复不是模型生成的，而是我们手写的。这样做是为了先看懂对话状态怎么流动。

#### 为什么返回 `{'messages': [reply]}`
节点返回的是一个只包含新回复的列表。

因为状态字段配置了 `add_messages`，所以 LangGraph 会把这个新回复追加到原来的消息列表后面。

最终结果中会同时包含：

- 用户原始消息
- AI 新回复

这就是对话状态的最小工作方式。

## 6. 使用大模型构建对话节点

现在把手写回复换成真正的大模型调用。

注意：下面代码会读取项目 `.env` 中的环境变量，因此第一步要先执行 `load_dotenv()`。

你需要在项目根目录配置：

```env
OPENAI_BASE_URL=你的接口地址
OPENAI_API_KEY=你的 API Key
```

```python
from dotenv import load_dotenv

load_dotenv()
```

### 代码解释

这段代码只有两行，但很重要。

#### `from dotenv import load_dotenv`
它从 `python-dotenv` 中导入 `load_dotenv` 函数。

#### `load_dotenv()`
它会尝试读取当前项目目录下的 `.env` 文件，并把里面的变量加载到当前 Python 进程中。

后面的 `ChatOpenAI` 会依赖 `OPENAI_API_KEY` 和 `OPENAI_BASE_URL`。

如果没有先执行这一步，Jupyter 很可能读不到环境变量，从而出现缺少 API Key 的报错。

```python
from typing import Annotated
from typing_extensions import TypedDict
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

llm = ChatOpenAI(model='qwen3.6-35b-A3b', temperature=0)

def chatbot(state: AgentState):
    response = llm.invoke(state['messages'])
    return {'messages': [response]}

builder = StateGraph(AgentState)
builder.add_node('chatbot', chatbot)
builder.add_edge(START, 'chatbot')
builder.add_edge('chatbot', END)

chat_graph = builder.compile()

result = chat_graph.invoke({
    'messages': [
        SystemMessage(content='你是一个通俗易懂的 Python 课程助教。'),
        HumanMessage(content='请用一句话解释什么是函数。')
    ]
})

print(result['messages'][-1].content)
```

### 代码解释

这是本节第一个真正调用大模型的对话代理。

#### `AgentState`
状态中只有一个字段：

```python
messages: Annotated[list, add_messages]
```

这表示整张图最重要的数据就是聊天记录。

#### `llm = ChatOpenAI(...)`
这里创建了一个聊天模型对象。

- `model='qwen3.6-35b-A3b'` 表示使用的模型名称
- `temperature=0` 表示回答尽量稳定，不要太随机

只要 `.env` 中配置了 `OPENAI_BASE_URL` 和 `OPENAI_API_KEY`，这里就可以正常使用对应接口。

#### `chatbot(state)` 节点
这是图里的核心节点。它做的事情是：

1. 读取当前状态中的 `messages`
2. 把完整消息列表传给大模型
3. 得到模型回复 `response`
4. 把回复追加回 `messages`

关键代码是：

```python
response = llm.invoke(state['messages'])
```

这不是只传最后一句用户问题，而是把整个消息列表传给模型。

#### 为什么返回 `[response]`
`response` 本身就是一个 AI 消息对象。

返回：

```python
{'messages': [response]}
```

表示把模型刚刚生成的回复追加到历史记录中。

#### 这张图的流程
整张图非常简单：

```
START -> chatbot -> END
```

虽然流程简单，但它已经具备对话代理的核心结构：用 `messages` 作为状态，用模型节点生成回复。

## 7. 多轮对话：手动传入历史消息

刚才的示例只运行了一轮。

如果想让模型记住前面说过什么，最直接的方法是：第二轮调用时，把第一轮返回的 `messages` 继续传进去。

```python
messages = [
    SystemMessage(content='你是一个简洁的中文助手。'),
    HumanMessage(content='我叫小王，正在学习 LangGraph。')
]

first_result = chat_graph.invoke({'messages': messages})
print('第一轮回答：')
print(first_result['messages'][-1].content)

second_messages = first_result['messages'] + [
    HumanMessage(content='我叫什么？我正在学什么？')
]

second_result = chat_graph.invoke({'messages': second_messages})
print('\n第二轮回答：')
print(second_result['messages'][-1].content)
```

### 代码解释

这个例子演示了最直接的多轮对话方式：手动保存并传递历史消息。

#### 第一轮对话
第一轮消息包括：

- 一条系统消息：规定助手要简洁
- 一条用户消息：告诉模型‘我叫小王，正在学习 LangGraph’

调用后，`first_result['messages']` 中会包含：

- 原来的系统消息
- 原来的用户消息
- 模型第一轮回复

#### 第二轮为什么要用 `first_result['messages']`
第二轮用户问：

```text
我叫什么？我正在学什么？
```

如果只把这句话传给模型，模型不知道答案。

所以代码这样写：

```python
second_messages = first_result['messages'] + [HumanMessage(...)]
```

意思是：把上一轮完整聊天记录拿过来，再追加新的用户问题。

#### 这个例子的局限
这种方式能工作，但需要我们自己手动管理 `messages`。

如果对话轮数很多，手动传来传去会比较麻烦。

所以 LangGraph 还提供了检查点机制，可以帮我们保存对话状态。

## 8. 使用检查点保存对话记忆

如果希望图自动保存多轮对话状态，可以使用检查点（checkpoint）。

最常见的入门方式是使用 `MemorySaver`。

它会根据 `thread_id` 保存不同会话的状态。

你可以把 `thread_id` 理解成一个聊天窗口 ID：

- 同一个 `thread_id`：共享同一段对话历史
- 不同 `thread_id`：互相独立，互不影响

```python
from langgraph.checkpoint.memory import MemorySaver

memory = MemorySaver()
chat_graph_with_memory = builder.compile(checkpointer=memory)

config = {'configurable': {'thread_id': 'student-001'}}

first_result = chat_graph_with_memory.invoke(
    {'messages': [HumanMessage(content='我叫小王，正在学习 LangGraph。')]},
    config=config
)
print('第一轮回答：')
print(first_result['messages'][-1].content)

second_result = chat_graph_with_memory.invoke(
    {'messages': [HumanMessage(content='我叫什么？我正在学什么？')]},
    config=config
)
print('\n第二轮回答：')
print(second_result['messages'][-1].content)
```

### 代码解释

这个例子是本节最接近真实对话机器人的写法。

#### `MemorySaver()`
`MemorySaver` 是一个内存版检查点保存器。

它会把图运行过程中的状态保存下来。

这里的状态主要就是 `messages`。

#### `builder.compile(checkpointer=memory)`
普通的 `compile()` 只是把图编译成可运行对象。

加上 `checkpointer=memory` 后，图在运行时会自动保存和读取状态。

#### `thread_id`
配置中最关键的是：

```python
config = {'configurable': {'thread_id': 'student-001'}}
```

它表示当前对话属于 `student-001` 这个会话。

只要第二次调用继续使用同一个 `thread_id`，LangGraph 就会自动接上之前的消息历史。

#### 为什么第二轮只传新消息也能记住上下文
第二轮调用时，我们只传了新的用户消息：

```python
{'messages': [HumanMessage(content='我叫什么？我正在学什么？')]}
```

但是因为 `thread_id` 没变，检查点里已经保存了上一轮的历史。

所以图会把旧消息和新消息合并起来，再交给模型。

这就是它能回答出‘你叫小王，正在学习 LangGraph’的原因。

#### 这个机制的价值
有了检查点机制，你不需要每次手动传完整历史。

这对真实聊天机器人非常重要，因为真实系统中会有很多用户、很多会话，每个会话都需要独立保存上下文。

## 9. 不同 thread_id 表示不同对话

为了理解 `thread_id`，可以再看一个例子。

同一个图，如果使用不同的 `thread_id`，就相当于打开了两个不同的聊天窗口。

```python
config_a = {'configurable': {'thread_id': 'chat-a'}}
config_b = {'configurable': {'thread_id': 'chat-b'}}

chat_graph_with_memory.invoke(
    {'messages': [HumanMessage(content='我叫小李。')]},
    config=config_a
)

chat_graph_with_memory.invoke(
    {'messages': [HumanMessage(content='我叫小张。')]},
    config=config_b
)

result_a = chat_graph_with_memory.invoke(
    {'messages': [HumanMessage(content='我叫什么？')]},
    config=config_a
)

result_b = chat_graph_with_memory.invoke(
    {'messages': [HumanMessage(content='我叫什么？')]},
    config=config_b
)

print('chat-a：', result_a['messages'][-1].content)
print('chat-b：', result_b['messages'][-1].content)
```

### 代码解释

这个例子用来说明：记忆不是全局混在一起的，而是按 `thread_id` 分开的。

#### `config_a` 和 `config_b`
这两个配置分别代表两个会话：

- `chat-a`
- `chat-b`

它们使用同一张图、同一个模型，但是历史记录互相独立。

#### 第一轮分别告诉不同名字
在 `chat-a` 中，用户说自己叫小李。

在 `chat-b` 中，用户说自己叫小张。

#### 第二轮都问‘我叫什么？’
虽然第二轮问题完全一样，但因为 `thread_id` 不同，模型看到的历史也不同。

所以理想情况下：

- `chat-a` 会回答小李
- `chat-b` 会回答小张

这就是多会话对话机器人的基础。

真实产品中，每个用户、每个聊天窗口、每个任务线程，都可以用不同的 `thread_id` 管理。

## 10. 对话代理的整体结构

到这里，我们可以把对话代理总结成下面这张流程图：

```
用户输入
  ↓
追加到 messages
  ↓
chatbot 节点读取 messages
  ↓
大模型基于完整上下文生成回复
  ↓
AI 回复追加到 messages
  ↓
检查点保存当前状态
```

其中最重要的两件事是：

- `messages` 负责保存对话内容
- `thread_id` 负责区分不同对话线程

理解这两点，就能看懂大多数 LangGraph 对话代理的基础写法。

## 11. 常见问题

### 11.1 为什么模型还是不记得前面说过的话
通常有几个原因：

- 没有把旧 `messages` 传入下一轮
- 没有使用 `add_messages`
- 使用检查点时，第二轮换了不同的 `thread_id`
- 每次都重新编译图并重新创建内存保存器

### 11.2 `messages` 会不会越来越长
会。

真实项目中通常需要做历史裁剪、摘要记忆或长期记忆存储。

本节先学习基础机制，后面再考虑复杂记忆管理。

### 11.3 `SystemMessage` 每轮都要传吗
如果你手动维护 `messages`，通常第一轮放进去后，后续继续传完整历史即可。

如果使用检查点，只要第一轮已经进入同一个 `thread_id`，后续通常不需要重复传同一条系统消息。

但在真实项目中，也有人会在每次调用前固定补充系统提示，保证行为稳定。

## 12. 本节小结

本节最重要的内容有五点：

1. **对话代理和一次性问答最大的区别是要保存历史上下文**
2. **`messages` 是对话状态的核心，负责保存多轮聊天记录**
3. **`add_messages` 可以让新消息追加到旧消息后面，而不是覆盖旧消息**
4. **对话节点通常会把完整 `messages` 传给聊天模型，再把模型回复追加回来**
5. **检查点和 `thread_id` 可以帮助我们自动保存不同会话的对话记忆**

掌握了本节内容，你就已经具备了构建基础聊天机器人的能力。后面再加入工具调用、条件边和长期记忆，就可以逐步扩展成更完整的智能体。
