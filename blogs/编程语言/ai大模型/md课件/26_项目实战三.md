# 26 项目实战三：带交互界面的智能体项目

## 学习目标
1. 完成一个具备完整交互界面的智能体项目
2. 掌握将 LangGraph 智能体与简单命令行界面集成
3. 能够进行项目测试、迭代和成果展示
4. 理解项目从需求分析到最终演示的完整开发流程
5. 学会把前面学过的状态、节点、边、条件分支组合成一个可用项目

本节课会完成一个小型项目：**学习任务助手**。

它可以根据用户输入，自动识别用户想做什么，并给出不同类型的回复。

## 1. 项目背景

前面的项目实战中，我们已经学习了知识库问答、多工具智能体等内容。

但是一个项目如果只能在代码单元里调用函数，体验还不够完整。

真实项目通常还需要一个交互入口，例如：

- 命令行界面
- Web 页面
- 桌面应用
- 聊天窗口
- 企业微信、飞书、钉钉机器人

本节我们先从最简单、最容易理解的命令行界面开始。

项目目标是做一个学习任务助手，用户可以输入自然语言，例如：

```text
帮我制定 LangGraph 学习计划
```

或者：

```text
解释一下条件边是什么
```

系统会根据输入内容判断用户意图，并给出对应回复。

## 2. 项目需求分析

做项目之前，先不要急着写代码。

我们先分析这个项目要具备哪些能力。

| 需求 | 说明 |
| --- | --- |
| 接收用户输入 | 用户可以输入一句自然语言请求 |
| 判断用户意图 | 判断用户是想学习计划、概念解释，还是普通聊天 |
| 生成对应回复 | 根据不同意图生成不同内容 |
| 保存执行状态 | 记录用户输入、意图、回复和历史记录 |
| 提供交互界面 | 让用户可以连续输入问题 |
| 支持测试和展示 | 能用示例输入验证系统是否正常 |

为了让项目容易运行，本节不依赖外部大模型 API，而是用规则模拟智能体的判断和回复。

这样做的好处是：

- 不需要 API Key
- 不受网络影响
- 更容易看清楚 LangGraph 的工作流结构
- 适合课堂演示和初学者练习

等理解项目结构后，再把规则回复替换成真实大模型也很容易。

## 3. 项目整体流程

学习任务助手的整体流程如下：

```text
用户输入
  ↓
分析意图
  ↓
根据意图选择处理节点
  ↓
生成回复
  ↓
记录历史
  ↓
返回结果
```

如果用 LangGraph 表达，可以拆成几个节点：

| 节点 | 作用 |
| --- | --- |
| `analyze_intent` | 分析用户意图 |
| `make_plan` | 生成学习计划 |
| `explain_concept` | 解释概念 |
| `chat` | 普通聊天回复 |
| `save_history` | 保存本轮对话历史 |

其中 `analyze_intent` 后面会接条件边，根据不同意图走到不同节点。

## 4. 第一步：定义项目状态

LangGraph 项目的第一步通常是定义状态。

状态可以理解为整个流程共享的数据记录。

本项目需要记录：

- 用户输入了什么
- 系统判断出的意图是什么
- 系统生成的回复是什么
- 历史对话有哪些

下面先定义状态结构。

```python
from typing_extensions import TypedDict

class AssistantState(TypedDict):
    user_input: str
    intent: str
    response: str
    history: list[str]

initial_state: AssistantState = {
    'user_input': '帮我制定 LangGraph 学习计划',
    'intent': '',
    'response': '',
    'history': []
}

print(initial_state)
```

### 代码解释

这段代码完成了项目状态设计。

#### `AssistantState`
这是一个 `TypedDict`，用来规定状态中有哪些字段。

字段含义如下：

- `user_input`：用户当前输入的内容
- `intent`：系统分析出的用户意图
- `response`：系统生成的回复
- `history`：保存历史交互记录

#### 为什么需要 `intent`
因为项目不是简单地收到输入就回复，而是要先判断用户想做什么。

例如：

- 用户说‘制定学习计划’，意图就是 `plan`
- 用户说‘解释条件边’，意图就是 `explain`
- 用户说‘你好’，意图就是 `chat`

后面条件边会根据 `intent` 决定走哪个处理节点。

#### 为什么需要 `history`
`history` 用来保存交互记录。

虽然本项目只是简单命令行助手，但保留历史可以帮助我们展示项目结果，也为后续扩展多轮对话打基础。

## 5. 第二步：编写意图识别节点

意图识别节点负责判断用户想做什么。

真实项目中，可以用大模型判断意图。

本节为了方便运行，先用关键词规则实现。

```python
def analyze_intent(state: AssistantState):
    text = state['user_input']

    if '计划' in text or '安排' in text or '学习路线' in text:
        intent = 'plan'
    elif '解释' in text or '什么是' in text or '概念' in text:
        intent = 'explain'
    else:
        intent = 'chat'

    return {'intent': intent}

test_state = {
    'user_input': '请解释一下 LangGraph 的条件边',
    'intent': '',
    'response': '',
    'history': []
}

print(analyze_intent(test_state))
```

### 代码解释

这个节点是项目中的第一个处理节点。

#### `text = state['user_input']`
从状态中取出用户输入。

后面的判断都基于这句话进行。

#### 关键词规则
代码中用了三类规则：

1. 如果包含 `计划`、`安排`、`学习路线`，判断为学习计划类需求
2. 如果包含 `解释`、`什么是`、`概念`，判断为概念解释类需求
3. 其他情况都归为普通聊天

#### 返回 `{'intent': intent}`
节点只返回要更新的字段。

这里不需要返回完整状态，因为 LangGraph 会把这个更新合并回原状态。

#### 为什么这里不用大模型
规则判断虽然简单，但非常适合教学。

它让我们先专注理解项目结构：

```text
输入 -> 判断意图 -> 条件分支
```

后续如果想升级，只需要把这个函数替换成大模型判断即可。

## 6. 第三步：编写不同意图的处理节点

识别出意图后，需要根据不同意图生成不同回复。

本项目设计三个处理节点：

- `make_plan`：生成学习计划
- `explain_concept`：解释概念
- `chat`：普通聊天

```python
def make_plan(state: AssistantState):
    response = '''这是一个建议的学习计划：
1. 先复习 LangGraph 的 State、Node、Edge
2. 再重点理解条件边和循环结构
3. 然后练习对话代理和工具调用
4. 最后完成一个小项目进行综合应用
'''
    return {'response': response}

def explain_concept(state: AssistantState):
    response = '''可以这样理解：
LangGraph 是一个用“图”来组织智能体流程的框架。
节点负责执行具体任务，边负责决定执行顺序，状态负责在节点之间传递数据。
'''
    return {'response': response}

def chat(state: AssistantState):
    response = '我可以帮你制定学习计划、解释 AI 智能体概念，或者协助你梳理项目思路。'
    return {'response': response}

print(make_plan(initial_state)['response'])
```

### 代码解释

这段代码定义了三个处理节点。

#### `make_plan`
当用户想要学习计划时，会进入这个节点。

它返回一个分步骤学习建议。

#### `explain_concept`
当用户想要解释概念时，会进入这个节点。

它用通俗语言解释 LangGraph 的核心思想。

#### `chat`
当系统没有识别到明确需求时，会进入普通聊天节点。

这个节点告诉用户当前助手能做什么。

#### 三个节点的共同点
它们都返回：

```python
{'response': response}
```

也就是说，它们都只负责生成回复，不负责保存历史，也不负责判断下一步。

这体现了项目开发中的一个好习惯：**每个节点只负责一件事。**

## 7. 第四步：保存历史记录

每轮交互结束前，我们希望把用户输入和系统回复保存下来。

这样后面展示项目成果时，就能看到完整历史。

```python
def save_history(state: AssistantState):
    new_record = f'用户：{state["user_input"]}\n助手：{state["response"]}'
    history = state['history'] + [new_record]
    return {'history': history}

sample_state = {
    'user_input': '你好',
    'intent': 'chat',
    'response': '你好，我是学习任务助手。',
    'history': []
}

print(save_history(sample_state))
```

### 代码解释

这个节点负责保存历史记录。

#### `new_record`
这一行把当前用户输入和助手回复拼成一条记录。

格式类似：

```text
用户：你好
助手：你好，我是学习任务助手。
```

#### `history = state['history'] + [new_record]`
这行代码不是直接修改原列表，而是创建一个新列表。

新列表 = 原来的历史记录 + 本轮新记录。

这样写更清晰，也更符合状态更新的思路。

#### 返回 `{'history': history}`
节点只更新 `history` 字段。

它不需要关心用户意图，也不需要重新生成回复。

这同样体现了节点职责分离。

## 8. 第五步：构建 LangGraph 工作流

现在我们已经有了所有节点，接下来把它们组装成一张图。

这张图的关键是：`analyze_intent` 后面要使用条件边。

不同意图会进入不同处理节点。

```python
from langgraph.graph import StateGraph, START, END

def route_by_intent(state: AssistantState):
    if state['intent'] == 'plan':
        return 'plan'
    if state['intent'] == 'explain':
        return 'explain'
    return 'chat'

builder = StateGraph(AssistantState)

builder.add_node('analyze_intent', analyze_intent)
builder.add_node('make_plan', make_plan)
builder.add_node('explain_concept', explain_concept)
builder.add_node('chat', chat)
builder.add_node('save_history', save_history)

builder.add_edge(START, 'analyze_intent')
builder.add_conditional_edges(
    'analyze_intent',
    route_by_intent,
    {
        'plan': 'make_plan',
        'explain': 'explain_concept',
        'chat': 'chat'
    }
)
builder.add_edge('make_plan', 'save_history')
builder.add_edge('explain_concept', 'save_history')
builder.add_edge('chat', 'save_history')
builder.add_edge('save_history', END)

assistant_graph = builder.compile()

print('图构建完成')
```

### 代码解释

这一段是项目的核心，把前面所有函数组装成完整工作流。

#### `route_by_intent`
这是路由函数，负责告诉条件边下一步去哪。

它根据 `state['intent']` 返回不同标记：

- `plan`
- `explain`
- `chat`

#### `builder.add_node(...)`
这些代码把节点加入图中。

节点本身只是 Python 函数，加入图之后才成为流程的一部分。

#### 条件边
核心代码是：

```python
builder.add_conditional_edges(...)
```

它表示：`analyze_intent` 执行完以后，不是固定走某一个节点，而是调用 `route_by_intent` 判断下一步。

映射关系是：

- `plan` -> `make_plan`
- `explain` -> `explain_concept`
- `chat` -> `chat`

#### 三个处理节点为什么都连到 `save_history`
不管用户意图是什么，最终都需要保存历史。

所以三个分支最后都会汇合到 `save_history`。

这就是图结构中的‘分支后汇合’。

#### 最终流程
完整执行路径可能是：

```text
START -> analyze_intent -> make_plan -> save_history -> END
```

也可能是：

```text
START -> analyze_intent -> explain_concept -> save_history -> END
```

具体走哪条路，由用户输入决定。

## 9. 第六步：测试单轮运行

在做交互界面之前，先测试图本身是否能正常运行。

这是项目开发中的好习惯：先测试核心逻辑，再做界面。

```python
state = {
    'user_input': '帮我安排一个 LangGraph 学习计划',
    'intent': '',
    'response': '',
    'history': []
}

result = assistant_graph.invoke(state)

print('识别意图：', result['intent'])
print('助手回复：')
print(result['response'])
print('历史记录：')
print(result['history'][0])
```

### 代码解释

这段代码测试了一次完整运行。

#### 初始状态
初始状态中，只有 `user_input` 是用户给出的。

其他字段先设置为空：

- `intent=''`
- `response=''`
- `history=[]`

这些字段会在图运行过程中被节点逐步填充。

#### `assistant_graph.invoke(state)`
这行代码启动整张图。

执行过程是：

1. `analyze_intent` 判断用户想要学习计划
2. 条件边把流程送到 `make_plan`

4. `save_history` 保存历史记录
5. 流程结束

#### 打印结果
最后打印三个重要信息：

- 系统识别出的意图
- 助手回复
- 历史记录

如果这一步结果正常，说明核心工作流没有问题。

## 11. 第八步：封装成一个函数

为了后面接入交互界面，我们把调用图的逻辑封装成函数。

这样界面部分只需要调用这个函数即可。

```python
def run_assistant(user_input, history=None):
    if history is None:
        history = []

    state = {
        'user_input': user_input,
        'intent': '',
        'response': '',
        'history': history
    }

    result = assistant_graph.invoke(state)
    return result

result = run_assistant('什么是 LangGraph？')
print(result['response'])
```

### 代码解释

这个函数是核心逻辑和交互界面之间的桥梁。

#### `run_assistant(user_input, history=None)`
它接收两个参数：

- `user_input`：用户输入
- `history`：历史记录，默认可以为空

#### 为什么默认值用 `None`
函数参数不建议直接写 `history=[]`。

因为列表是可变对象，作为默认参数可能带来意外共享问题。

所以这里写成：

```python
if history is None:
    history = []
```

这是 Python 中比较稳妥的写法。

#### 函数内部做了什么
函数内部重新构造状态，然后调用：

```python
assistant_graph.invoke(state)
```

最后把结果返回。

有了这个函数，后面无论是命令行界面还是 Web 界面，都可以复用同一套智能体逻辑。

## 12. 第九步：构建命令行交互界面

现在我们给项目加一个简单的命令行界面。

用户可以连续输入内容，输入 `退出` 时结束。

注意：在 Jupyter Notebook 中，`input()` 需要手动输入。如果你只是阅读课件，可以先不运行这一格。

```python
def start_cli():
    print('学习任务助手已启动')
    print('你可以输入问题，例如：帮我制定学习计划 / 解释条件边 / 你好')
    print('输入“退出”结束对话')

    history = []

    while True:
        user_input = input('你：')

        if user_input.strip() == '退出':
            print('助手：再见，祝你学习顺利！')
            break

        result = run_assistant(user_input, history)
        history = result['history']

        print('助手：')
        print(result['response'])

# 在 notebook 中如需体验交互，可以取消下一行注释
# start_cli()
```

### 代码解释

这段代码实现了一个简单但完整的命令行交互界面。

#### `start_cli()`
这是启动命令行界面的函数。

运行后，用户可以不断输入问题。

#### `history = []`
这里创建一个历史记录列表。

每一轮调用助手后，都会更新历史。

#### `while True`
这是一个循环，让程序可以一直等待用户输入。

如果没有这个循环，程序只能回答一次。

#### `input('你：')`
这是命令行输入入口。

用户在这里输入自然语言请求。

#### 退出逻辑
如果用户输入：

```text
退出
```

程序会打印告别语，并用 `break` 跳出循环。

#### 调用智能体
核心代码是：

```python
result = run_assistant(user_input, history)
```

这说明界面层并不直接处理智能体逻辑。

它只是把用户输入交给 `run_assistant`，再把结果展示出来。

这种分层方式很重要：

- LangGraph 负责智能体逻辑
- `run_assistant` 负责封装调用
- `start_cli` 负责用户交互

这样项目结构更清晰，也更容易维护。

## 13. 第十步：模拟一次完整展示

课堂演示或项目展示时，不一定要真的手动输入。

```python
demo_inputs = [
```

这段代码模拟了一次完整项目演示。

1. 普通聊天
2. 学习计划
3. 概念解释

这样可以展示项目的三个主要能力。

```python
history = result['history']
```

这样三轮对话会保存在同一个历史列表中。

#### 为什么适合成果展示
这种方式不用手动输入，运行一次就能展示完整效果。

在课堂演示、录屏展示、项目答辩中都很方便。

#### `len(history)`
最后打印历史记录数量。

## 14. 项目可以如何继续迭代

当前项目是一个最小可用版本。

如果继续升级，可以从下面几个方向入手。

| 迭代方向 | 说明 |
| --- | --- |
| 接入真实大模型 | 用 ChatOpenAI 替换规则回复 |
| 增加更多意图 | 支持总结、翻译、代码解释等能力 |
| 加入工具调用 | 让助手可以查询资料、计算、读取文件 |
| 使用检查点 | 保存多轮对话状态 |
| Web 界面 | 用 Gradio、Streamlit 或 FastAPI 做页面 |
| 持久化历史 | 把历史记录保存到文件或数据库 |

项目开发通常不是一次写完，而是不断从 MVP 迭代。

本节完成的是第一版：能运行、能交互、能展示。

## 15. 本节小结

本节完成了一个完整的交互式智能体小项目。

你需要重点掌握以下几点：

1. **项目开发要先做需求分析，再写代码**
2. **状态设计决定了智能体流程中能传递哪些信息**
3. **节点负责具体任务，条件边负责根据意图选择路径**
4. **核心逻辑要先测试，再接入交互界面**
5. **命令行界面虽然简单，但已经能体现完整项目闭环**

到这里，我们已经把 LangGraph 的基础能力组合成了一个可演示、可测试、可继续迭代的项目。
