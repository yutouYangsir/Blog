# 22_任务调度型智能体

## 学习目标
1. 理解任务调度型智能体的设计思路
2. 掌握使用 LangGraph 实现任务分解、执行与结果汇总
3. 能够构建简单的自动化任务处理智能体

本节课会用一个通俗例子来理解任务调度：**把一个大任务拆成多个小任务，再安排合适的节点依次完成，最后汇总结果**。

## 1. 什么是任务调度型智能体

任务调度型智能体可以理解为一个“项目经理型”智能体。用户只提出一个目标，它不会马上盲目执行，而是先思考：

1. 这个目标可以拆成哪些步骤？
2. 哪些步骤需要先做，哪些步骤可以后做？
3. 每一步应该交给哪个工具、函数或智能体执行？
4. 每一步完成后，如何把结果合并成最终答案？

例如用户说：

> 帮我分析一个产品的用户反馈，并给出改进建议。

任务调度型智能体可能会拆成：

1. 收集用户反馈
2. 对反馈进行分类
3. 提取高频问题
4. 生成改进建议
5. 输出结构化报告

这类智能体的核心不是“单次回答”，而是“组织多个步骤完成复杂任务”。

## 2. 任务调度的基本流程

一个典型任务调度型智能体通常包含 4 个环节：

| 环节 | 作用 | 通俗理解 |
| --- | --- | --- |
| 任务输入 | 接收用户目标 | 用户告诉智能体要做什么 |
| 任务分解 | 把大任务拆成小任务 | 项目经理制定待办清单 |
| 任务执行 | 按顺序执行每个小任务 | 不同同事完成各自工作 |
| 结果汇总 | 整合所有执行结果 | 写成最终报告交给用户 |

在 LangGraph 中，我们可以把每个环节看成一个 **节点**，节点之间通过 **边** 连接起来，形成一个工作流。

## 3. 先不用 LangGraph：用普通 Python 理解任务调度

在学习 LangGraph 前，先用普通 Python 模拟一个最小任务调度流程。这个例子不依赖任何外部库，更容易理解“任务分解、执行、汇总”的本质。

```python
def split_task(user_goal):
    """把用户的大目标拆成多个小任务。"""
    tasks = [
        f"理解用户目标：{user_goal}",
        "收集与目标相关的信息",
        "分析关键信息",
        "生成最终建议",
    ]
    return tasks


def execute_task(task):
    """模拟执行一个小任务。"""
    return f"已完成：{task}"


def summarize_results(results):
    """把多个小任务的执行结果汇总成最终输出。"""
    report = "任务执行报告：\n"
    for index, result in enumerate(results, start=1):
        report += f"{index}. {result}\n"
    return report


user_goal = "为一家咖啡店设计会员运营方案"
tasks = split_task(user_goal)
results = [execute_task(task) for task in tasks]
final_report = summarize_results(results)

print(final_report)
```

### 代码解释

这段代码展示了任务调度的最小模型：

1. `split_task(user_goal)` 负责拆解任务。它接收用户的大目标，返回一个任务列表。
2. `execute_task(task)` 负责执行单个小任务。这里为了演示，只返回“已完成”的文字。真实项目中，这里可以调用搜索工具、数据库、LLM 或其他业务函数。
3. `summarize_results(results)` 负责汇总结果。它把每个小任务的输出整理成最终报告。
4. `results = [execute_task(task) for task in tasks]` 是任务调度的执行阶段，会逐个执行任务列表里的每一项。

这个例子虽然简单，但已经包含任务调度型智能体最重要的 3 个动作：**拆、做、汇总**。

## 4. LangGraph 的核心概念

LangGraph 是一个用“图”组织智能体流程的框架。

可以把它想象成一张流程图：

```text
开始 -> 任务分解 -> 任务执行 -> 结果汇总 -> 结束
```

在 LangGraph 中常见概念如下：

| 概念 | 含义 | 通俗理解 |
| --- | --- | --- |
| State | 工作流中流动的数据 | 一个不断更新的任务档案袋 |
| Node | 处理数据的函数 | 流程图中的一个步骤 |
| Edge | 节点之间的连接 | 告诉程序下一步去哪里 |
| Graph | 完整工作流 | 整张流程图 |

接下来我们用 LangGraph 实现同样的“拆、做、汇总”流程。

## 6. 定义工作流状态 State

State 是 LangGraph 中非常重要的概念。它表示工作流运行过程中一直携带和更新的数据。

本例中，我们希望 State 保存 4 类信息：

1. `goal`：用户输入的大目标
2. `tasks`：拆分后的小任务列表
3. `results`：每个小任务的执行结果
4. `final_answer`：最终汇总答案

```python
from typing import List, TypedDict


class TaskState(TypedDict):
    goal: str
    tasks: List[str]
    results: List[str]
    final_answer: str
```

### 代码解释

这段代码定义了工作流中的数据结构：

1. `TypedDict` 用来描述字典里应该有哪些字段。它不会改变程序运行方式，但能让代码更清晰。
2. `TaskState` 表示整个任务调度过程中共享的数据。每个节点都会读取它，也可以返回新的字段值更新它。
3. `goal: str` 表示用户目标是字符串。
4. `tasks: List[str]` 表示任务列表，里面每一项都是字符串。
5. `results: List[str]` 表示执行结果列表。
6. `final_answer: str` 表示最终回答。

可以把 `TaskState` 理解为一张任务表，工作流每走一步，就在这张表上补充一些内容。

## 7. 编写节点函数

节点函数就是工作流中的一个步骤。每个节点接收当前 `state`，处理后返回要更新的字段。

下面定义 3 个节点：

1. `planner_node`：任务分解节点
2. `worker_node`：任务执行节点
3. `summary_node`：结果汇总节点

```python
def planner_node(state: TaskState):
    goal = state["goal"]
    tasks = [
        f"明确目标：{goal}",
        "列出目标用户和使用场景",
        "设计可执行的行动步骤",
        "整理成清晰的建议清单",
    ]
    return {"tasks": tasks}


def worker_node(state: TaskState):
    results = []
    for task in state["tasks"]:
        result = f"完成任务：{task}"
        results.append(result)
    return {"results": results}


def summary_node(state: TaskState):
    lines = ["最终任务调度结果："]
    for index, result in enumerate(state["results"], start=1):
        lines.append(f"{index}. {result}")
    final_answer = "\n".join(lines)
    return {"final_answer": final_answer}
```

### 代码解释

这段代码定义了 3 个节点函数：

1. `planner_node(state)`：从 `state["goal"]` 读取用户目标，然后生成 `tasks` 任务列表。返回 `{"tasks": tasks}` 表示把任务列表写回 State。
2. `worker_node(state)`：读取 `state["tasks"]`，循环执行每个任务。这里用字符串模拟执行结果，真实项目中可以替换为调用工具、调用模型、查询数据库等操作。
3. `summary_node(state)`：读取 `state["results"]`，把多个结果拼接成一段最终答案。

需要注意：节点函数通常不需要返回完整 State，只返回自己负责更新的字段即可。LangGraph 会把这些字段合并回当前 State。

## 8. 用 LangGraph 连接节点

现在有了节点函数，下一步就是把这些节点连成一张图。

流程如下：

```text
START -> planner -> worker -> summary -> END
```

```python
from langgraph.graph import END, START, StateGraph


workflow = StateGraph(TaskState)

workflow.add_node("planner", planner_node)
workflow.add_node("worker", worker_node)
workflow.add_node("summary", summary_node)

workflow.add_edge(START, "planner")
workflow.add_edge("planner", "worker")
workflow.add_edge("worker", "summary")
workflow.add_edge("summary", END)

app = workflow.compile()
```

### 代码解释

这段代码把节点组织成可运行的工作流：

1. `StateGraph(TaskState)` 创建一张图，并说明这张图中的数据结构是 `TaskState`。
2. `add_node("planner", planner_node)` 把 `planner_node` 注册成名为 `planner` 的节点。
3. `add_edge(START, "planner")` 表示工作流从 `planner` 节点开始。
4. `add_edge("planner", "worker")` 表示任务分解完成后，进入任务执行节点。
5. `add_edge("worker", "summary")` 表示任务执行完成后，进入结果汇总节点。
6. `add_edge("summary", END)` 表示汇总完成后，工作流结束。
7. `workflow.compile()` 会把流程图编译成一个可以调用的应用对象 `app`。

这一步相当于把流程图画好，并告诉程序每一步应该怎么走。

## 9. 运行任务调度智能体

工作流编译完成后，就可以传入用户目标并运行了。

```python
initial_state = {
    "goal": "为一家咖啡店设计会员运营方案",
    "tasks": [],
    "results": [],
    "final_answer": "",
}

final_state = app.invoke(initial_state)

print(final_state["final_answer"])
```

### 代码解释

这段代码负责真正运行工作流：

1. `initial_state` 是初始状态，里面放入用户目标 `goal`，其余字段先给空值。
2. `app.invoke(initial_state)` 会启动 LangGraph 工作流。数据会依次经过 `planner`、`worker`、`summary` 三个节点。
3. 运行结束后返回 `final_state`，它包含整个流程运行后的完整状态。
4. `final_state["final_answer"]` 取出最终汇总结果并打印。

从这个例子可以看到，LangGraph 的优势是把复杂流程拆成清晰节点，每个节点只负责一件事。

## 10. 加入条件判断：根据任务复杂度选择路径

真实任务中，不是所有问题都需要复杂调度。

例如：

- 简单问题：直接回答即可
- 复杂问题：先拆分，再执行，再汇总

LangGraph 支持条件边，可以根据 State 的内容决定下一步走哪条路径。

```python
from typing import Literal


def judge_complexity(state: TaskState) -> Literal["simple", "complex"]:
    goal = state["goal"]
    if len(goal) <= 12:
        return "simple"
    return "complex"


def direct_answer_node(state: TaskState):
    answer = f"这是一个简单任务，可以直接处理：{state['goal']}"
    return {"final_answer": answer}
```

### 代码解释

这段代码新增了两个函数：

1. `judge_complexity(state)` 用来判断任务复杂度。这里为了教学简单，用目标文字长度作为判断标准：短任务走 `simple`，长任务走 `complex`。真实项目中可以让大模型判断复杂度。
2. `Literal["simple", "complex"]` 表示这个函数只会返回两个固定值之一，方便我们理解后续条件分支。
3. `direct_answer_node(state)` 是简单任务的处理节点，不做任务分解，直接生成最终答案。

这个例子说明：任务调度不一定永远走同一条流程，可以根据任务情况动态选择路径。

## 11. 构建带条件分支的工作流

下面把简单路径和复杂路径组合到同一张图里。

```python
branch_workflow = StateGraph(TaskState)

branch_workflow.add_node("direct_answer", direct_answer_node)
branch_workflow.add_node("planner", planner_node)
branch_workflow.add_node("worker", worker_node)
branch_workflow.add_node("summary", summary_node)

branch_workflow.add_conditional_edges(
    START,
    judge_complexity,
    {
        "simple": "direct_answer",
        "complex": "planner",
    },
)

branch_workflow.add_edge("direct_answer", END)
branch_workflow.add_edge("planner", "worker")
branch_workflow.add_edge("worker", "summary")
branch_workflow.add_edge("summary", END)

branch_app = branch_workflow.compile()
```

### 代码解释

这段代码构建了一个带分支的任务调度工作流：

1. `add_conditional_edges` 表示添加条件边。它会先调用 `judge_complexity`，再根据返回值选择下一步。
2. 如果返回 `simple`，流程进入 `direct_answer` 节点，然后直接结束。
3. 如果返回 `complex`，流程进入 `planner` 节点，再继续执行 `worker` 和 `summary`。
4. 这张图有两条路径：一条适合简单任务，一条适合复杂任务。

这就是任务调度型智能体的一个关键能力：**不是固定执行所有步骤，而是根据任务情况选择合适流程**。

## 12. 测试条件分支效果

分别输入一个简单任务和一个复杂任务，观察工作流走向的差异。

```python
simple_state = {
    "goal": "写标题",
    "tasks": [],
    "results": [],
    "final_answer": "",
}

complex_state = {
    "goal": "为一家咖啡店设计会员运营方案，并给出执行步骤",
    "tasks": [],
    "results": [],
    "final_answer": "",
}

print("简单任务结果：")
print(branch_app.invoke(simple_state)["final_answer"])

print("\n复杂任务结果：")
print(branch_app.invoke(complex_state)["final_answer"])
```

### 代码解释

这段代码测试了条件分支：

1. `simple_state` 的目标是“写标题”，文字较短，所以 `judge_complexity` 返回 `simple`，流程会直接进入 `direct_answer`。
2. `complex_state` 的目标更长，所以返回 `complex`，流程会进入 `planner -> worker -> summary`。
3. 两次都调用 `branch_app.invoke(...)`，但由于输入不同，工作流自动选择了不同执行路径。

这说明任务调度型智能体可以做到“简单任务快速处理，复杂任务分步处理”。

## 13. 小结

本节课学习了任务调度型智能体的基本设计方法：

1. 任务调度型智能体适合处理多步骤、复杂目标。
2. 它的核心流程是：任务输入、任务分解、任务执行、结果汇总。
3. LangGraph 可以把每个步骤定义成节点，并用边连接成工作流。
4. State 是工作流中流动的数据，节点通过读取和更新 State 协同完成任务。
5. 条件边可以让智能体根据任务情况选择不同执行路径。

掌握这些内容后，就可以继续扩展：把 `worker_node` 替换成真实工具调用、搜索引擎调用、数据库查询或大模型调用，从而构建更实用的自动化任务处理智能体。
